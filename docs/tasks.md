# 剩余 Agent 任务

按顺序执行，每段代码块是一轮会话。开始前阅读 README、docs/api.md 和本地 AGENTS.md，检查当前代码与已有改动。每轮只实现一项，完成后说明修改、实际验证和未验证项；不新增进度流水，不提交密钥，不自动推送。

## 第2周：完成自然语言问路

### 1. 业务工具

```text
为模型接入 search_places、get_campus_connectors、plan_journey 三个 Java 工具，复用现有 PlaceService、CampusConnectorService、JourneyService。
保持普通查询接口不变；工具参数严格校验，未知工具不执行。路线数字来自服务结果，模型不得改写。
验收：合法输入调用相应服务并返回结构化结果；未知工具、非法参数不执行服务；用明确预期验证参数传递及错误映射。
```

### 2. 单轮问路接口

```text
前置：业务工具已完成。
实现 POST /api/assistant/query 的单轮问路，请求包含用户消息，返回回答、执行状态和结构化 JourneyPlan；先确定并更新 docs/api.md 中的契约，再接入现有模型客户端和工具循环。
验收：真实模型理解“从图书馆去天府广场，少走路”，调用 Java 工具并返回真实路线；费用、时间、步行距离与工具结果一致。离线与真实服务验证分别报告。
```

### 3. 缺失条件与地点消歧

```text
前置：单轮问路接口。
缺起点或终点时返回待补充状态；同名/多个候选时返回候选 ID 与待确认字段。确认前不执行行程查询，不猜测当前位置。
验收：缺起点、缺终点、未知地点、同名地点各一例；确认候选后使用对应稳定 ID 查询。
```

### 4. 会话持久化

```text
前置：确认接口已确定；具备可用的 MySQL 测试库。
基于现有 Flyway 三张表实现匿名会话的 Repository 和事务，保存条件、确认状态、有序消息和行程快照；使用 owner token 哈希隔离会话，版本检查防止旧响应覆盖。
验收：重启后恢复条件；不同 owner 无法读取或修改；并发修改不会覆盖新状态；事务失败不留下半条会话。更新迁移时保留已发布的 V1。
```

### 5. 多轮修改终点

```text
前置：会话持久化。
支持“改去春熙路”：保留已确认起点、出发时间和偏好，更新终点并实际重新调用 JourneyService。
验收：先查天府广场，再改春熙路；响应 ID、终点和路线更新，其余条件保留；旧请求晚到时不能覆盖新结果。
```

### 6. 多轮修改偏好

```text
前置：多轮终点修改。
支持“少走路”“少换乘”“按推荐”：只修改偏好，保留地点和时间并重查。排序沿用 Java 逻辑，不让模型自行重排权威结果。
验收：三种偏好正确映射；新结果与直接调用普通接口一致；无新路线时明确反馈，不编造变化。
```

### 7. 小程序聊天输入

```text
前置：问路接口与确认契约。
增加聊天页面，支持发送、加载、失败重试、补充条件和点击候选确认。服务密钥留在后端；请求与会话隔离，重复点击及旧响应不产生错误状态。
验收：完整操作一次问路、补充起点、候选确认、网络失败重试；原普通表单继续可用。页面不出现任务号、接口字段或交接说明。
```

### 8. 聊天展示路线

```text
前置：聊天输入。
聊天响应复用现有 JourneyCard、JourneyDetail、JourneyMap；卡片选择与地图来自同一结构化方案。模型不可用时普通表单仍可查询，地图服务失败时不得展示静态路线冒充真实结果。
验收：问路、改终点、改偏好各走通一次；无方案、模型超时、地图超时后无旧路线残留。
```

### 9. 扩展校园起点

```text
基于来源数据扩展至6–10个校园起点、至少2个可用校门。逐项保留位置角色、坐标系、地图估算方法和通行确认依据。
应用核实结论维护在 backend/src/main/resources/data/，不把来源候选直接改成已核实。东门进出方向节点不能为缩减数据而删掉。
验收：每个新增起点均有可追溯接驳，跨校门的时间推进和边界点一致；不能确认的继续保留不可用状态。
```

### 10. 手机端验收

```text
前置：真实高德配置、手机和开发者工具可用。
按 README 从干净目录启动，在手机完成图书馆→天府广场、切换偏好、切换方案、查看地图、失败重试；聊天功能完成后追加一轮问路及修改条件。
验收：真实网络与真实服务全部走通；分别报告模拟器与手机结果，不用构建成功代替真机。只保留必要的最终演示素材。
```

## 第3周：选做

```text
前置：核心问路与真机已通过。
一次只做一个步骤：①扩展期望到达时间契约；②Java 根据实际方案计算能否按时到达；③表单展示判断；④模型提取到达约束；⑤回归验证。
完成标准：边界时刻、跨日和未知耗时有明确处理，不承诺实际准点；没有反向路线查询时只评价候选，不编造最晚出发时刻。
```

## 第4周：交付

```text
一次完成一个交付项并验收：①部署 HTTPS 后端与微信网络配置；②另一台设备按 README 独立复现；③回归普通表单、问路、确认、多轮、异常与真机；④录制演示；⑤完成 OPC 分工、成本、用户反馈与迭代报告；⑥核实参赛要求并准备材料。
最终完成标准：源码、数据来源、运行说明、真实服务与真机验证、演示视频及报告齐备。只写实际完成的参赛与部署状态。
```
